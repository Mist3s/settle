## ADR-001: Хостинг — VPS с Let's Encrypt

**Дата:** 2026-04-29
**Статус:** принято
**Вопрос архитектуры:** 17.A

### Контекст

Архитектура предлагает два варианта: VPS с публичным HTTPS или локальный
сервер за VPN. Решение влияет на CSP, JWT-cookie стратегию и мониторинг.

### Рекомендация

**VPS с Let's Encrypt** (дефолт из архитектуры).

**Обоснование:**
- Доступ к приложению откуда угодно без настройки VPN-клиента.
- Стандартная цепочка HTTPS с валидным сертификатом — нет проблем с CORS,
  Mixed Content, Service Worker.
- Certbot в docker-compose — автоматическое обновление сертификатов.
- Мониторинг и бэкапы проще: хост всегда доступен, cron работает 24/7.
- Для одного пользователя с финансовыми данными — JWT + HTTPS достаточная
  защита, VPN — избыточен.

### Отвергнутая альтернатива

Локальный сервер за VPN: усложняет первоначальную настройку, требует
Wireguard/Tailscale клиент на каждом устройстве, при выключении сервера —
данные недоступны.

## ADR-002: Стратегия досрочного погашения по умолчанию — `reduce_payment`

**Дата:** 2026-04-29
**Статус:** принято
**Вопрос архитектуры:** 17.B

### Контекст

При частичном досрочном погашении банк применяет одну из двух стратегий:
уменьшение платежа или сокращение срока. Большинство российских банков
по умолчанию уменьшают платёж, но часть позволяет выбирать.

### Рекомендация

**`reduce_payment`** как дефолт на уровне импорта и создания кредита.

**Обоснование:**
- Типичное поведение Альфа, Сбер, Яндекс Банк при подаче заявки на
  досрочное погашение без явного указания стратегии.
- Безопаснее для пользователя: меньший ежемесячный платёж снижает риск
  кассового разрыва.
- Стратегия переключается на уровне каждого кредита — если банк
  фактически сократил срок, пользователь меняет после первого факта.

### Действие при первом досрочном погашении

1. Зарегистрировать факт досрочного платежа.
2. Сравнить расчётный новый график с реальным из банковского приложения.
3. Если расхождение — сменить `prepayment_strategy` кредита.
4. UI подсказывает это при первом досрочном по каждому кредиту.

## ADR-003: Граница `underpayment` / `missed` — нулевой платёж = `missed`

**Дата:** 2026-04-29
**Статус:** принято
**Вопрос архитектуры:** 17.C

### Контекст

Модель различает `underpayment` (заплатил меньше) и `missed` (не заплатил
вовсе). В банковской реальности `missed` влечёт пени и штрафы, которые
в первой версии не реализуются.

### Рекомендация

**Граница:** `amount == 0` → `missed`, `0 < amount < planned` → `underpayment`.

**Архитектурный задел:**
- Добавить nullable-поле `loans.late_fee_rate NUMERIC(5,4)` уже в первой
  миграции. Заполнение = NULL, расчёт пеней — не реализуется.
- В `PaymentService` при регистрации `missed` — warning-лог и UI-алерт
  «пени не рассчитаны, обратитесь в банк».
- Это позволит добавить расчёт пеней в будущем без миграции схемы.

### Отвергнутая альтернатива

Считать `missed` разновидностью `underpayment` (amount=0) — теряется
семантика, сложнее фильтровать историю и строить аналитику.

## ADR-004: Точность калькуляторов — сверка после первого факта

**Дата:** 2026-04-29
**Статус:** принято
**Вопрос архитектуры:** 17.D

### Контекст

Часть плановых платежей размечена как `calculated_annuity` или `estimate`.
Реальные графики банков могут отличаться из-за кэшбека, страховки,
изменения ставки в течение срока.

### Рекомендация

**Порог расхождения:** 1% от суммы платежа.

**Процедура:**
1. При регистрации первого `actual_payment` по каждому кредиту,
   если `accuracy ∈ {calculated_annuity, estimate}`:
   - Вычислить расхождение: `|actual - planned| / planned`.
   - Если > 1% — UI показывает предупреждение: «Фактический платёж
     отличается от расчётного на X%. Рекомендуем обновить параметры
     кредита или ввести точный график».
2. Пользователь может:
   - Обновить ставку/срок → пересчитать график.
   - Загрузить точный график через импорт (`exact_contract` / `exact_screenshot`).
   - Проигнорировать (система запомнит, больше не покажет для этого кредита).

### Решение по «корректирующему коэффициенту»

Не вводить в первой версии. Корректировка через обновление параметров
кредита (ставка, срок) или через импорт точного графика — проще и
прозрачнее. Коэффициент может маскировать реальные ошибки.

## ADR-005: Импорт как пакет `services/import_/` вместо монолитного файла

**Дата:** 2026-04-29
**Статус:** принято
**Вопрос архитектуры:** реализация §11 (раздел 6 плана)

### Контекст

План предполагал `services/import_service.py` — один файл. При оценке
объёма оказалось ~580 строк только для committer, плюс парсер, валидатор,
diff, оркестратор. Monolith превышал порог 400 строк из AGENTS.md.

### Решение

Разбить на пакет `services/import_/` из 7+ модулей:
- `storage.py` — in-memory TTL store (64 строки)
- `header_validator.py` — валидация заголовков (107 строк)
- `parser.py` — XLSX→DTO (205 строк)
- `cross_validator.py` — кросс-валидация (160 строк)
- `diff.py` — build_diff (245 строк)
- `committer_core.py` + `committer_loans.py` + `committer_payments.py` + `committer.py` — commit (597 строк, 4 файла)
- `orchestrator.py` — public API (~110 строк)
- `__init__.py` — тонкий реэкспорт

### Обоснование

- Каждый модуль ≤280 строк, тестируется изолированно.
- Четкая ответственность: парсинг, валидация, diffing, commit — независимые стадии.
- `committer` разбит на 4 файла из-за repetitive audit boilerplate по 6 типам сущностей.

### Отвергнутая альтернатива

Один файл ~1200 строк — превышает порог, сложнее тестировать и ревьюить.

## ADR-006: CLI на argparse вместо typer/click

**Дата:** 2026-04-29
**Статус:** принято
**Вопрос архитектуры:** §11.5 CLI

### Контекст

План предполагал typer или click. Проект уже имеет зависимость на FastAPI
(Pydantic v2), но не на typer/click. CLI содержит 4 команды, ~166 строк.

### Решение

Использовать `argparse` из stdlib.

### Обоснование

- Ноль дополнительных зависимостей.
- 4 команды (template, import, export) — trivial для argparse.
- typer добавляет transitive зависимость (click + typer + rich), не оправданную для 4 команд.

### Отвергнутая альтернатива

typer — удобнее для больших CLI, но overhead для 4 команд не оправдан.
