Ты реализуешь проект **Settle** — персональный веб-трекер долгов,
платежей и симулятор финансовых сценариев. Стек: FastAPI +
PostgreSQL + React/TypeScript в Docker. Один пользователь.

## Источник истины

`architecture.md` в корне репозитория — авторитетная спецификация.
Прочитай целиком перед планированием. Любое отклонение от
архитектуры требует явного согласования и фиксируется как ADR
в `docs/decisions.md`.

## Где живут артефакты

Любой результат длиннее десятка строк идёт в файл, а не в чат.

- План реализации → `docs/implementation-plan.md`
- Решения по открытым вопросам и отклонения от архитектуры
  → `docs/decisions.md` (по одному ADR на решение)
- Текущее состояние проекта → `docs/state.md`
- Журнал выполненного → `docs/progress.md`
- Заметки по этапам, чек-листы, временные обсуждения → `docs/notes/`

В чат — только короткое резюме (5–15 строк): что сделано, что
требует моего решения, ссылка на файл с деталями.

## Что должен содержать план

В файле `docs/implementation-plan.md`:

1. Таблица этапов: номер, название, сложность (S/M/L), зависимости,
   ссылка на якорь с деталями. 8–15 этапов в порядке выполнения,
   охватывающих весь объём раздела 16.1 архитектуры без дробления
   и пропусков.
2. По каждому этапу секция: предусловия, что делается, артефакты,
   критерий готовности. Кратко, без дублирования.
3. Граф зависимостей (Mermaid).
4. Открытые вопросы из раздела 17 архитектуры с рекомендацией
   по каждому — для последующей фиксации в decisions.md.
5. Риски и митигации — таблицей.

Сложность относительная (S/M/L), без человеко-дней.

## Реализация: мелкие коммиты внутри этапа

Один «этап» из плана — это серия логически связанных коммитов,
не один гигантский. Внутри этапа коммить по мере готовности
изолированных кусков (одна модель + миграция, один сервис +
тесты, один роутер + интеграционный тест и т.д.).

Если файл при создании становится длиннее ~400 строк — это
сигнал разбить его логически (модели по сущностям, сервисы
по доменам, роутеры по ресурсам), а не запихивать всё в один.

## Память между чатами

Контекст между этапами передаётся через файлы:

- `docs/implementation-plan.md` — план целиком, неизменяемый
  без апрува.
- `docs/state.md` — текущее состояние. Обновляется в начале
  и в конце каждого этапа.
- `docs/progress.md` — журнал. Дописывай запись по этапу
  в конце, не переписывай предыдущие.
- `docs/decisions.md` — ADR. Любое нетривиальное решение
  фиксируется как отдельная запись с датой, контекстом,
  выбранным вариантом, отвергнутыми альтернативами.

В конце каждой atomic-задачи (до закрытия чата на ней):

1. Прогнать `ruff check app/` и `pytest` — всё чисто и зелёное.
2. Закоммитить (Conventional Commits) и запушить.
3. Дописать одну строку в `docs/progress.md`.
4. Обновить `docs/state.md` (курсор на следующую задачу).

В конце каждого этапа дополнительно:

5. Финальный обзорный абзац в `docs/progress.md` по этапу
   (≤30 строк): что вошло, ключевые модули, итоговое число
   тестов, известные ограничения.
6. Если возникли решения, отклоняющиеся от архитектуры или
   закрывающие открытые вопросы — добавить ADR в
   `docs/decisions.md`.
7. Финальный коммит этапа: `feat(<scope>): complete stage N`.

Если задача прерывается посреди работы — сделать WIP-коммит,
в `state.md` зафиксировать точку остановки и что осталось.

В начале нового чата восстанови контекст из этих файлов в
порядке: state → progress → decisions → implementation-plan →
точечно architecture.md (только нужные разделы).

## Жёсткие правила

- В финансовом контуре только `decimal.Decimal`. `float`
  в `services/`, `domain/`, `repositories/` — баг.
- Soft delete и `audit_log` на всех пользовательских данных
  с первого этапа, не «потом добавим».
- Импорт идемпотентен по бизнес-ключам из раздела 11.4
  архитектуры — покрывается тестом, иначе импорт не считается
  готовым.
- Pydantic-схемы запросов: `ConfigDict(extra='forbid')`.
- Симулятор overlay НЕ пишет в основные таблицы. Отдельный
  тест на этот инвариант.
- JWT с первого этапа.
- Критические тесты финансового движка из раздела 14.3
  пишутся одновременно с кодом, не после.
- **Тесты пишутся одновременно с кодом, не после.** Каждый
  новый роутер, сервис, constraint или поведение сопровождается
  тестом в том же коммите. Код без тестов не считается готовым.
- **`ruff check` должен проходить чисто перед каждым коммитом.**
  Запускать `ruff check app/` внутри контейнера и исправлять
  все ошибки до `git commit`. Не коммитить с нарушениями
  линтера.

## Конвенции

- Код, имена файлов, ключи API, имена листов и колонок шаблона
  импорта — английский, `snake_case`.
- UI и сообщения об ошибках — русский.
- Комментарии — английский, только где «зачем» не очевидно.
- Коммиты — Conventional Commits.

## Гранулярность работы

Прежде чем писать код, оцени объём задачи:

- Один файл ожидаемо <200 строк → реализуй сразу с тестом.
- Один файл ожидаемо ≥200 строк → ОБЯЗАТЕЛЬНО разбей его
  на пакет из 3–6 модулей по ответственностям, опиши пакет
  в docs/notes/, и реализуй модули поочерёдно — каждый
  модуль не более одного хода.
- В одной задаче >2 файлов нетривиального размера → стоп.
  Запроси у меня декомпозицию задачи на atomic-подзадачи
  через `docs/notes/stageN_breakdown.md` и не начинай писать
  код до апрува декомпозиции.

Если ты замечаешь, что не успеваешь в один ход — это сигнал,
что задача была слишком крупной. Не начинай писать код частями
в надежде «дотянуть». Останови работу, зафиксируй это в
docs/state.md, попроси декомпозицию.

## Чего не делать

- Не предлагать альтернативный стек.
- Не задавать вопросы, ответы на которые есть в `architecture.md`.
  Спрашивай только про реально неопределённое.
- Не вводить новые сущности БД без правки `architecture.md`
  и апрува.
- Не писать «TODO: добавим позже» в финансовой логике.
- Не вываливать длинные ответы в чат — всё содержательное в файлы.
- Не коммитить код без тестов и без прогона линтера.
